## 1. 결론

커밋된 EXP-10 결과는 R0.2.1의 목표인 **동일한 계산을 dependency 경계에서 중단·저장·복원·재개해도 판단·proof·memory·기존 연산 의미가 유지되는가**에 대해 통과 결과를 기록한다. 다음의 제한된 M 전문화 실험을 설계할 기준선으로 사용할 수 있다.

이번 성과는 정답률·속도 향상이 아니라 **진행 중 계산 상태의 지속성과 실행 방식의 동등성**이다. EXP-09에서 확인했던 약한 입력의 오수렴, 회로 우회 후 수정, 다른 부분회로를 사용한 재오답은 그대로 보존됐다.

## 2. 이번 검토의 실제 범위

원격 커넥터로 커밋을 고정하고 다음을 읽었다.

- 결과 `summary.ko.md`, `summary.json`, `audit.json`, `plan.json`, `manifest.json`.
- 원시 `main/resumed/checkpoint_io.jsonl` 60행 전체.
- 원시 `budget/legacy/record.json`, `budget/resumed/record.json`.
- 현재 `src/hcr/sessions.py`, `src/hcr/evaluation/session_protocol.py`의 저장·복원·대조 경로.
- 기존 배포자료에서 읽은 `session_audit.py` 등 관련 코드. 로컬 열람한 핵심 코드 5개는 결과 manifest에 기록된 SHA-256과 같음을 확인했다.

실제로 추가 수행한 검사는 다음이다.

1. main의 저장·복원 60개 journal 수치 열을 Python으로 재집계했다.
2. budget 원시 기록 2개를 읽어 대조했고, 실행 시간 차이와 그에 따른 이벤트 해시 체인을 제외하면 동일함을 계산으로 확인했다. 바이트 재구성은 manifest SHA-256과 Git blob SHA가 모두 일치한 경우에만 채택했다.
3. 저장·복원 API가 검증된 JSON으로 새로운 engine 객체를 복원한다는 코드를 대조했다.

**이번 답변에서 전체 52개 checkpoint를 새로 내려받아 감사기를 재실행한 것은 아니다.** 아래 전역 audit 수치는 저장소에 커밋된 감사 결과이며, 이번에 별도로 수행한 budget 비교·journal 재집계와 구분한다. 새 HCR 추론, 소스 수정, 커밋·push는 수행하지 않았다.

## 3. 관찰: 세 실행 방식의 대조

| 실행 방식 | 실제 코드 경로 |
|---|---|
| legacy | 현재 코드의 `AdaptiveEngine.infer()` |
| continuous | 동일 진행 API를 session으로 중단 없이 실행 |
| resumed | 각 전이 뒤 JSON 저장 → load → 다음 전이 수행 |

4개 조건군 × legacy와 다른 방식 2개의 비교로 **8개 대조 모두 통과**했다. 판단, assessment, 공개 관측, 외부 참값, memory, engine 이벤트가 모두 동등하다고 기록돼 있다. 비교에서 제외한 것은 `cost.wall_seconds`와 시간 변화로 달라지는 이벤트 SHA 체인이다.

| 조건군 | 방식당 판단 기록 | continuous 대조 | resumed 대조 |
|---|---:|---|---|
| main | 7 | 일치 | 일치 |
| unknown | 1 | 일치 | 일치 |
| budget | 1 | 일치 | 일치 |
| no_reexpansion | 1 | 일치 | 일치 |

합계는 비교 추론 30회다. 사전 seed 학습 6회는 별도다. 30회는 30개의 독립 과제가 아니라 10개 판단 위치를 세 방식으로 실행한 수다.

저장된 audit는 다음을 보고한다.

| 항목 | 기록된 검사 수/상태 |
|---|---:|
| checkpoint 검사 | 52 |
| 외부 판단 재평가 | 36 |
| final engine 이벤트 검사 | 1,624 |
| source_checked | true |
| verified | true |
| audit 중 new_inferences | 0 |

52개는 seed·최종 상태·중간 checkpoint가 포함된 검사 건수다. 서로 독립적인 새 표본 52개나 서로 다른 복구 과제 52개를 뜻하지 않는다.

## 4. 관찰: 성공뿐 아니라 오류·보류 경계도 유지

| 사례 | 출력 | 정답 여부 | primitive proof D | tick | expansion |
|---|---|---|---:|---:|---:|
| familiar | True | True | 3 | 69 | 2 |
| counterfactual | False | True | 2 | 96 | 2 |
| longer | True | True | 4 | 105 | 2 |
| branch | True | True | 2 | 64 | 1 |
| weak_conflict | True | False | 3 | 75 | 1 |
| same_score_revision | False | True | 2 | 39 | 3 |
| retention | True | False | 3 | 88 | 2 |

| unknown | None | None | 해당 없음 | 59 | 2 |
| budget | None | None | 해당 없음 | 0 | 1 |

약한 입력의 최초 오답은 길이 3 회로 `pattern-ac8909863fce4682a84bf769`를 사용한다. 동일점수 재시도는 회로 없이 정답을 내고, 다음 retention은 길이 2 회로 `pattern-d7053e8a62ed20d50b15444c`를 사용해 다시 틀린다. 이 동작이 세 실행 방식에서 같다.

특히 budget의 원시 기록을 별도로 대조하면 `max_expansions=1`에서 한 번 확장하고 `budget_exhausted`로 보류한다. 복원했다고 예산이 새로 생기거나 완료하지 않은 경로를 proof로 만드는 행동은 이 사례에서 보이지 않는다. 사용 시간은 legacy 약 0.496 ms, resumed 약 0.524 ms로 다르지만, 나머지 판단·비용·이벤트 의미는 같다.

unknown의 `None`과 budget의 `None`은 올바른 정답 출력으로 세지 않는다. 또한 부정 정답 `False`와 보류 `None`은 다르다.

## 5. 해석: 이번에 확보된 계산 구조

R0.2의 memory save/load는 주로 이미 학습된 회로를 보존하는 기능이었다. R0.2.1에서는 그보다 넓게, 현재 frontier·진행 상태·판단 이력·revision 권한·누적 비용을 다음 실행으로 전달할 수 있다.

이는 이후 전문화된 처리기를 번갈아 실행하거나, 한 처리기의 중간 결과를 다른 처리기에 전달하는 M 실험에 필요한 기반이다. 단, 현재 `resumed`는 매 전이 뒤 같은 프로세스에서 실제 파일을 저장하고 새 객체로 load하는 대조다. 전체 EXP-10이 OS 프로세스를 종료·재기동하는 실험은 아니다. 별도 프로세스 resume 시험은 테스트 코드에 따로 존재하며 두 검증을 혼동하지 않는다.

또한 하나의 dependency step 안의 pool/decision settle은 끝까지 수행된다. 임의 kernel tick에서 중단하는 실험이나, 멈춘 동안 내부 activation이 자율적으로 계속 변하는 실험은 아니다. `generation`은 begin/advance/finish/feedback/request_revision 등의 실행 전이 번호이며 `D_DAG`가 아니다.

## 6. 새로 확인한 비용: 상태 보존·검산 관리 비용

`main/resumed/checkpoint_io.jsonl`의 30개 save와 30개 load를 다시 합산했다.

| 항목 | 재집계 결과 |
|---|---:|
| save | 30회 / 약 1.673178초 |
| load | 30회 / 약 1.942483초 |
| save+load | 약 3.615661초 |
| 누적 checkpoint 기록량 | 9,280,292 bytes |
| 누적 checkpoint 읽기량 | 9,280,292 bytes |
| 첫 checkpoint | 24,202 bytes |
| 마지막 checkpoint | 537,873 bytes |
| 첫 save+load | 약 28.082 ms |
| 마지막 save+load | 약 202.457 ms |

여기서 시간은 디스크 I/O만이 아니다. 코드상 save/load에는 checkpoint 검산, 직렬화·역직렬화, engine 복원이 포함된다. 전체 run 시간도 아니며 seed/final 저장·전이 deepcopy·추론·마지막 전체 audit 등은 이 합계에 포함하지 않는다.

현재 packet에는 engine 상태 외에 events와 transitions 전체가 들어가며 저장과 복원 양쪽에서 검산한다. 따라서 이 기록에서는 history가 누적되면서 checkpoint 크기와 관리 시간도 커진다. 이것은 `판단 연산 카운터 동일`과 `전체 실행 비용 동일`이 다르다는 구체적 사례다. 다만 각 구성의 시간 비중을 별도로 계측한 것은 아니므로, 3.62초 중 특정 비율이 디스크 또는 검산 때문이라고 단정하지 않는다.

다음 M 비교에서 매 처리기 교대마다 디스크 save/load를 강제하면 방법 효과와 checkpoint 비용이 섞인다. 메모리 내 step interleaving을 주 비교로, checkpoint는 별도의 내구성 검사 조건으로 유지하는 설계를 제안한다.

## 7. 대안 설명과 측정 경계

### 7.1 legacy의 의미

legacy는 이전 R0.2 커밋의 동결 실행파일이 아니라 현재 `AdaptiveEngine.infer()`다. 따라서 이 EXP-10만으로 과거 버전과 현재 버전의 모든 의미가 보존됐다는 결론까지 확대하지 않는다. 현재 버전 내 실행 방식의 동등성과, 별도로 수행한 버전 간 차등 검사는 구분한다.

### 7.2 세 경로가 같은 엔진을 쓰므로 일치한 것 아닌가

공통 엔진을 사용하는 것은 의도된 통제다. JSON 저장·복원은 상태 유실·stale reference·누적 비용 초기화 등 추가 실패점을 만든다. 이번 대조는 이 직렬화 경계를 넘어서도 같은 결과와 이력이 유지되는지를 확인한다. 반면 공통 계산 정책 자체의 정확성을 독립적으로 입증하는 대조는 아니다. proof/외부 평가와 state audit가 별도로 필요한 이유다.

### 7.3 과거 branch 63 ticks와 이번 64 ticks

EXP-09의 원시 비용 입력은 diamond의 네 edge가 모두 참·score 0.92였다. 현재 EXP-10 generator는 `diamond('e104', (False, True, True, True), ...)`를 사용한다. 동일 입력 비교가 아니므로 63→64만으로 회귀 오류나 비용 증가를 판정하지 않는다. 이번 수용 기준은 EXP-10 안의 동일 관측을 세 방식으로 실행했을 때 일치하는가다.

### 7.4 상태 동등성이 오수렴의 해결을 뜻하지 않음

이 단계의 성공은 실패를 없애는 것이 아니라 원래 실패와 수정 경로를 보존하는 것이다. prior의 역할, 부정 예외 학습, 겹치는 회로의 오류 배분, pool 비용은 여전히 각각 별도 개입 대상이다.

## 8. 다음 판별 실험

권장 다음 단계는 로드맵의 R0.3 최소 M 실험이다. 먼저 같은 입력·표현·memory·총예산에서 다음을 비교한다.

| 비교 | 구별할 설명 |
|---|---|
| primitive 우선 vs learned macro 우선 | 방법별 탐색 순서·prior 적용·후보 선택의 차이 |
| 두 방법의 고정 배분 vs mismatch 기반 적응 배분 | 배분 정책 자체의 기여 |
| 메모리 내 interleaving vs checkpoint 삽입 | 방법 효과와 상태 관리 비용의 분리 |

결합 조건에만 두 배 예산을 주지 않는다. 총 kernel/pool/primitive 비용을 합의된 단위별로 제한하고, 공통 근거가 처리기 사이를 돌아온 것을 새 증거로 중복 계산하지 않는다. prior routing-only 개입은 scheduler·부정 예외학습 변경과 별도 조건으로 둔다.

R0.2.1은 동일 상태의 직렬화·재개 기반으로 수용하되, R0.3 이전에 전체 구조를 다시 설계하거나 같은 EXP-10을 이유 없이 반복할 필요는 없다. 이후 변경에서도 이번 기록을 회귀 기준으로 계속 사용한다.

## 9. 현재 주장 가능한 범위

> 고정된 symbolic toy-world와 R0.2 계산 정책에서, dependency 경계의 session 상태를 JSON으로 저장·복원해 재개하는 실행은 중단 없는 실행과 판단·primitive proof·memory·기존 연산 카운터·engine 이벤트의 의미를 유지했다. 오수렴·보류·revision 제한도 해당 사례에서 유지됐다. 추가 checkpoint 관리 비용은 별도로 발생했으며, 전체 성능 개선을 검증한 결과는 아니다.
