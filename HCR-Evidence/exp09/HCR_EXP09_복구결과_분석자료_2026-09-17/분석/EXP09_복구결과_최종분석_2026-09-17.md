# EXP-09 r2 복구 결과 수용·분석

작성일: 2026-09-17
대상: 사용자 첨부 `r02-diagnostic-01-recovered.zip`
분석 범위: 첨부 요약·감사 기록·실행 당시 소스·원시 이벤트 및 이전에 첨부한 실패 ZIP과의 대조. 새 추론·학습·저장소 수정 없음.

## 1. 최종 판정

**복구가 정상 완료됐고, 기존 60회 실행을 보존한 채 요약·감사 자료를 생성했다.** 이번 복구로 바뀐 것은 결과 수용 절차이며, 엔진의 정답·오답이나 계산 성능이 아니다. 같은 실행의 재집계이므로 새로운 실험 표본 또는 독립 재현으로 더하지 않는다. [S1–S5]

연구적 결과는 다음과 같다. 저장·복원은 같은 동작을 유지한다. 회로 사용으로 dependency 확장은 줄지만 이번 다섯 과제에서는 전체 tick·신호 연산·기록 포함 추론시간이 증가했다. 오류 feedback은 선택된 회로를 약화하지만 겹치는 다른 부분회로를 통한 재오답을 막지 못했다. 추가 관측 없이도 회로를 우회한 계산은 해당 약한 입력에서 정답을 냈다. [S3, S5–S7]

**따라서 EXP-09 복구·기록 수용 단계는 종료하고 R0.2.1의 상태 보존 구현으로 진행해도 된다.** snapshot/restore/resume의 성공 기준은 기존 동작을 그대로 재현하는 것이다. 학습 정책이나 prior·pool 비용 개선을 같은 변경에 섞지 않는다. 이는 아래 검산과 결과에 근거한 개발 순서 제안이다.

해시·원본 대조·집계 확인은 이번 분석에서 별도로 작성한 검사로 수행했다. 수치 재계산·proof·학습 전이 재검산은 첨부된 `recovery_tool_source/recover_probe.py::verify_recovery`와 동결된 감사 보조 함수를 다시 사용했다. 이를 전부 새로운 독립 구현이라고 부르지 않는다. 생산 inference 모듈(`hcr.runtime`, `hcr.learning`, `hcr.dynamics`, `hcr.expansion`)은 import하지 않았다.

첨부 receipt에는 사용자의 복구 실행에서 `baseline_capture_verified=true`라고 기록되어 있다. 이번 첨부에는 전체 baseline capture가 없으므로 이 분석은 포함된 `baseline_contract.json`·동결 source·원시 기록을 대조했다. 전체 capture를 다시 읽어 확인했다고 보고하지 않는다. 또한 전체 frontier 정책 재생과 wall-clock 시간 재측정은 수행 범위가 아니다. [S1–S2, V1]

### 실패 상태와 복구 완료 상태가 함께 있는 이유

```text
original/FAILED.json  → 원래 실행은 요약 단계에서 실패
receipt.json         → state=complete, original_run_state=failed
audit.json           → verified=true, differences=[]
summary.json         → reanalysis_complete=true, records_complete_for_plan=true
new_inferences       → 0
```

이는 모순이 아니라 원본 이력과 복구 결과의 분리다. `original_completion_manifest_verified=false`도 원본에 완료 manifest가 없었다는 뜻이며, 이번 복구 감사의 실패 표시가 아니다.

## 3. 요약기 오류는 올바른 비교 계약으로 해소됐다

동일점수 재시도군과 정밀측정 재시도군은 서로 다른 실행 ID를 가진다. 이 ID가 학습 이력에 남으므로 memory 전체 해시는 다르다. 복구 결과는 이 차이를 지우지 않고 다음을 별도로 표시한다. [S3: correction_controls.memory_comparison]

| 비교 항목 | 결과 |
|---|---|
| 첫 오류 전 memory 문서 | 동일 |
| 오류 후 원본 문서 전체 | 다름 (`exact_document_equal=false`) |
| 실행 ID의 정해진 참조 필드 대응 | 유효 |
| 대응 후 문서 전체 비교 | 동일 |
| 실제 상태 동등성 | 참 |
| 비교에서 삭제한 필드 | 없음 (`excluded_fields=[]`) |

실제로 달랐던 4곳은 `circuits[1].feedback_ids[6]`, `consumed_feedback[6]`, `patches[6].decision_id`, `patches[6].feedback_id`다. strength·활성 여부·실패 횟수·pending·version·기존 이력을 무조건 무시한 결과가 아니다. 저장·복원 대조에서는 여전히 동일 문서 전체 해시를 검사한다.

## 5. 저장·복원과 장기 학습 효과는 다르다

직접 memory를 사용한 조건과 같은 memory를 save/load한 조건은 전체 memory 문서·해시, ID와 실측 시간을 제외한 판단·연산량, 외부 평가가 모두 같았다. 두 조건 모두 길이 2 부분회로를 사용해 `True`를 출력했고, 정답은 `False`여서 둘 다 오답이다. [S3: persistence; S5]

**이 대조에서 저장 손상 때문에 다시 틀린 것은 아니다. 수정 후 memory가 새 약한 입력에서도 같은 오수렴을 만드는 것이 문제다.** 저장·복원 계약의 통과와 오류 교정의 일반화 성공을 하나로 세지 않는다.

### 어떤 회로가 약화됐고 무엇이 다시 사용됐는가

| 부분회로 | 최초 오류 전 강도 | 오류 직후 강도 | 새 약한 입력에서 사용 |
|---|---:|---:|---|
| 길이 3 | 0.81015625 | 0.16203125 | 아니오 |
| 길이 2 | 0.81015625 | 0.81015625 | 예, edge [0,1] |

길이 3 회로로 첫 오답을 낸 뒤 해당 회로만 약화됐다. 새 입력에서는 약화되지 않은 길이 2가 선택되어 첫 두 edge를 처리하고, 마지막 edge를 전개하면서 다시 오답에 도달했다. 길이 2는 정밀측정 입력에서는 정상 구간 [1,2]에도 쓰였다. 따라서 모든 길이 2 회로를 일괄 폐기하는 처방은 정상 재사용까지 훼손할 수 있다. [S6–S7]

총 10개 feedback update 중 회로 내용이 실제 바뀐 것은 최초 오류 뒤 약화 5개다. `value=False`로 정답이 된 후의 feedback 5개는 모두 `changes=[]`, `circuit_state_changed=false`였고 이력만 증가했다. 현재 update_adaptive의 참인 검증 경로만 컴파일하는 조건과 일치한다. **수정 판단을 얻은 것과 부정 예외를 장기 지식으로 학습한 것은 다르다.** [S7–S8]

## 6. 추가 관측 없이도 해당 입력을 수정할 수 있었다

다음 표의 출력은 엔진의 True/False이며 정답 여부와 다르다. 이 conflict world의 정답은 False다. [S3: factorial; S5]

| memory / 입력 / 회로 | 출력 | 정답 여부 | 총 ticks |
|---|---|---|---:|
| before/weak/circuits | True | 오답 | 75 |
| before/weak/graph_only | False | 정답 | 39 |
| before/measured/circuits | False | 정답 | 96 |
| before/measured/graph_only | False | 정답 | 28 |
| after/weak/circuits | True | 오답 | 88 |
| after/weak/graph_only | False | 정답 | 39 |
| after/measured/circuits | False | 정답 | 95 |
| after/measured/graph_only | False | 정답 | 28 |

동일점수 재시도는 첫 edge의 -0.06을 유지한 채 회로를 우회하여 39 ticks에 정답이 됐다. 정밀측정 재시도는 -0.98로 강화하여 같은 회로 우회 상태에서 28 ticks에 정답이 됐다. 여기서 추가 관측은 더 빠른 수렴에 기여했지만 정답 도달에 필수는 아니었다. 외부 오류 feedback도 정보라는 사실과 구분하여, “추가 정보 전혀 없이 학습됐다”라고 표현하지 않는다. 원래 memory의 `before/weak/graph_only`도 feedback 학습 없이 정답이라는 별도 대조가 있다.

`runtime.py::AdaptiveEngine.infer`의 재시도는 `use_circuits=self.use_circuits and not forced`를 적용한다. 즉 이 성공은 회로를 켠 채 잘못된 attractor를 수정한 실험이 아니라, 회로를 우회한 primitive 재계산이다. [S8]

### 최종 판단 네트워크까지 대조한 결과

수정 전 약한 입력의 circuits/graph-only는 공개 입력·memory·최종 Program 구조·Program digest·top_down 설정이 같았다. 차이는 circuits 조건이 경로 node `p:0:0`, `p:0:1`, `p:0:2`와 `goal`에 prior 1.3055089285714285를 추가했다는 점이다. [S5: r02_network; V2: weak_pair_final_network]

그 결과 첫 edge의 활성도는 graph-only에서 0.1954374761, circuits에서 0.5642279599였다. 판단 경계 0.5를 사이에 두고 가정이 반대로 나뉜다. 공개 score를 바꿔 쓴 것이 아니라 동일한 관측이 회로 prior와 재귀 신호가 있는 계산에서 다르게 해석됐다.

소스에서도 adaptive_network는 회로 prior를 경로 node와 goal의 drive에 추가한다. 따라서 이번 구현에서 회로는 단순 탐색 shortcut뿐 아니라 사실 판단을 편향시키는 역할도 한다. “구조의 익숙함을 routing에만 활용하는 조건”과 “판단 drive에도 전달하는 기존 조건”을 분리할 이유가 이 기록과 소스에서 확인된다. 이것은 후속 개입 제안이며 이번에 그 변경을 실행한 것은 아니다.

## 7. 탐색 압축과 총비용 개선은 분리해야 한다

5사례마다 같은 공개 입력·학습 memory에서 graph_only/circuits를 4쌍씩 비교했다. 각 사례에서 두 종류의 실행 순서는 각각 2회였으며 40개 판단 모두 정답이다. [S3: benchmark; S5]

| 사례 | graph 중앙값 ms | circuit 중앙값 ms | 중앙값의 비율 | 확장 graph→circuit | tick graph→circuit |
|---|---:|---:|---:|---|---|
| same_structure | 3.395 | 10.409 | 3.07배 | 3→2 | 36→69 |
| counterfactual | 2.974 | 13.371 | 4.50배 | 3→2 | 28→96 |
| renamed_reordered | 3.382 | 10.654 | 3.15배 | 3→2 | 36→69 |
| longer_composition | 4.183 | 15.233 | 3.64배 | 4→2 | 38→105 |
| branched_composition | 3.076 | 9.604 | 3.12배 | 2→1 | 33→63 |

확장 횟수는 33~50% 감소했지만 모든 사례에서 총 tick·신호·추론 시간이 증가했다. 이 입력 범위에서 비용 절감 목표를 달성했다고 평가할 수 없다. 측정 시간은 기록 처리를 포함한 infer 구간이며 초기화·학습·save/load를 모두 합한 end-to-end 시간은 아니다. [S3: benchmark.timing_scope]

동일 구조 사례에서는 graph-only 36 ticks에 비해 circuits는 pool 34 + decision 35 = 69 ticks였다. 최종 판단에서 1 tick을 줄이는 대신 후보 경쟁에 34 ticks를 추가했다. 신호도 graph-only 432에 비해 circuits는 pool 884 + decision 420 = 1,304였다.

| 사례 | pool 신호 | 전체 circuit 신호 | pool 비중 |
|---|---:|---:|---:|
| same_structure | 884 | 1304 | 67.79% |
| counterfactual | 1198 | 1546 | 77.49% |
| renamed_reordered | 884 | 1304 | 67.79% |
| longer_composition | 1224 | 1816 | 67.40% |
| branched_composition | 682 | 938 | 72.71% |

이는 연산 카운터 비중이며 CPU 시간 점유율은 아니다. pool/decision은 전체의 세부 내역이므로 전체에 다시 더하지 않는다. paired delta의 중앙값과 두 중앙값의 차이는 계산법이 달라 같을 필요가 없고, 제공된 summary의 paired delta는 원시 기록에서 다시 계산해 일치함을 확인했다.

각 비용 쌍에서 primitive proof D는 같았다. 한편 오답에서 정답으로 수정될 때의 D=3→2는 긍정 경로 증명에서 차단 edge를 사용하는 부정 증명으로 바뀐 결과다. proof.py는 부정 결론을 path_blocked→all_paths_blocked로 복원한다. 이 D 변화를 회로 학습이 동일 proof의 깊이를 압축했다는 증거로 세지 않는다. [S8: proof.reconstruct]

## 8. 학습 횟수와 오답 수렴

| 학습 횟수 | 강도 | prior | pool ticks | 판단 ticks | 최초 오답 총 ticks | 수정 ticks |
|---:|---:|---:|---:|---:|---:|---:|
| 3 | 0.550000 | 0.775500 | 41 | 51 | 92 | 28 |
| 6 | 0.810156 | 1.305509 | 36 | 39 | 75 | 28 |
| 9 | 0.919910 | 1.556487 | 35 | 37 | 72 | 28 |

학습 횟수가 증가한 조건에서 같은 오답에 더 적은 tick으로 수렴했다. pool뿐 아니라 최종 판단 network에서도 51→39→37 ticks로 감소했다. 따라서 빠른 수렴과 정답이 같지 않다는 구체적인 구현 관측으로 남길 수 있다.

이 비교는 학습 횟수 조작이다. strength뿐 아니라 evidence 수와 balance도 바뀌어 prior를 함께 결정하므로 strength 하나만 독립 조작했다고 부르지 않는다. 수정 시에는 모두 회로를 우회하므로 28 ticks가 동일한 결과로 강한 회로의 수정 난이도가 같다고 결론 내릴 수 없다.

## 9. 남은 범위와 다음 구현

### 종료해도 되는 작업

요약 오류 재현·수정, 실행 ID 대응 계약, 원시 60개 기록의 계획 조건 충족, 복구 산출물 해시·집계·감사 확인은 이번 묶음에서 완료됐다. 같은 기록을 다시 복구하거나 같은 자료를 다시 제출할 필요는 없다.

### R0.2.1에서 보존할 동작

| 보존할 기준 | snapshot/restore/resume 수용 조건 제안 |
|---|---|
| direct/reload가 같은 오답을 낸 사례 | 복원 과정이 판단·memory 의미를 바꾸지 않는다 |
| 길이 3 약화 후 길이 2 재선택 | frontier·binding·memory version·prior 연결을 유지한다 |
| 같은 점수 회로 우회 재시도는 정답 | revision 권한·요청 상태·회로 스위치를 유지한다 |
| pool + decision 비용 합계 | 중단·재개 뒤 기존 연산을 누락·중복 계상하지 않는다 |
| 최초 오답과 수정 정답은 별도 기록 | 복원 과정에서 최초 실패를 덮어쓰지 않는다 |

checkpoint 자체의 저장·복원 비용은 별도 계측한다. 수치 상태, frontier, program digest, 역할 binding, 대기 revision, memory version을 함께 보존하고, 기존 판단 계산의 의미를 고정한다.

학습/정확도 개선은 그다음 별도 대조로 수행한다. 후보는 routing prior와 판단 prior 분리, 오류 binding/조건에 제한된 예외 학습, 정상 부분회로 보존이다. 비용 개선은 pool 비용과 대체되는 decision 계산을 분리하여 평가한다. 전체 회로를 일괄 약화하거나 후보 경쟁을 무조건 없애는 처방을 이번 결과만으로 채택하지 않는다.

### 측정되지 않은 것

초기화 시간, save/load 시간, 전체 probe end-to-end 시간은 원래 실패 전 파일에 남지 않아 null로 보존됐다. 0으로 대체하거나 사후 복원했다고 주장하지 않는다. 전체 frontier 정책의 독립 재생도 이번 감사 범위 밖이다. [S2–S3]
