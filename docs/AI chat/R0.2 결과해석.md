결론부터 말하면, **이번 review는 정상적으로 끝났고 R0.2의 현재 상태를 꽤 명확하게 분해해줬다.** 특히 중요한 건 “무엇이 실제로 관찰됐고, 무엇은 아직 원인으로 말할 수 없는지”가 깔끔하게 갈렸다는 점이다.

먼저 무결성부터 보면 문제없다. capture 무결성 검사가 통과했고, 원본 capture를 수정하지 않았으며, 새 inference도 실행하지 않았다. 분석 대상은 기존 R0.2 기록 36개다.  manifest도 `state=complete`이고 review/receipt 파일 해시가 기록돼 있다. 

### 1. R0.2에서 확인된 오답은 전부 같은 표면 패턴이다

36개 기록 중 내가 집계하면:

* 정답: **31**
* 오답: **5**
* 오답 5개 모두 `stable_decision`
* 오답 5개 모두 `misconvergence`
* 동시에 모두 `assumption_reality_mismatch`

였다.

구체적으로 오답이 나온 곳은:

```text
misconvergence/full           attempt 1
misconvergence/no_reexpansion attempt 1
retention/reload              attempt 1
tradeoff/training_3           attempt 1
tradeoff/training_9           attempt 1
```

이다. 보고서에도 이 다섯 구간이 그대로 나타난다.  

이건 꽤 중요한 관찰이다.

현재 발생한 오류는:

```text
계산 불능
non-convergence
oscillation
proof 자체 붕괴
```

형태가 아니라,

> **내부적으로는 안정적으로 결론을 냈고 proof도 구성했지만, 그 계산이 전제로 삼은 상태가 현실/외부 조건과 맞지 않았다**

는 형태다.

즉 현재 toy world 안에서는 네가 생각했던 **“빠르고 안정적으로 틀리는 상태”**가 실제로 존재한다.

## 2. feedback + re-expansion 효과는 상당히 선명하다

`misconvergence/full`을 보면:

```text
attempt 1
correct = false
proof D = 3
assumptions = 3
misconvergence

↓

attempt 2
correct = true
proof D = 2
assumptions = 1
```

로 바뀐다. 

반면:

```text
misconvergence/no_reexpansion
```

에서는 첫 오답에서 끝난다. 

이건 R0.2에서 가장 강하게 볼 수 있는 결과 중 하나다.

현재 증거 범위에서 말할 수 있는 것은:

> **오류 신호 뒤 추가 계산을 허용하는 경로가 실제 결론을 바꿨다.**

다.

그리고 단순히 답 문자열만 바뀐 것도 아니다.

```text
proof D:       3 → 2
assumption:    3 → 1
positive ones: 3 → 0
```

로 실제 계산 구조가 달라졌다.

이건 `Circuit → mismatch → Graph Expansion → revised decision` 구조가 최소 toy-world 수준에서는 행동 차이를 만든다는 증거다.

---

# 3. 그런데 retention은 현재 중요한 미해결점이다

가장 주목해야 할 것은 이거다.

```text
retention/reload
correct = false
stable_decision
misconvergence
assumption_reality_mismatch
proof D = 3
```



즉 직전 episode에서 feedback을 받아 수정할 수 있었지만, **새 episode의 같은 약한 측정 profile에서는 다시 기존 유형의 오수렴이 발생했다.**

이건 무시하면 안 된다.

현재 결과가 말하는 건:

```text
같은 episode 안 수정 가능
≠
다음 episode에도 수정 효과가 일반화됨
```

이라는 것이다.

다만 여기서 곧바로:

> “memory 저장이 실패했다.”

라고 결론 내리면 안 된다.

이번 review 자체가 명시적으로 원인을 판정하지 않았다. `cause_status = not_identified_by_this_review`이고, activation failure / binding failure / competition failure / over-compression / graph-expansion failure를 원인으로 확정하지 않았다. 

그래서 이건 **다음 원인분리 실험의 최우선 대상**이다.

# 4. Familiarity Compression에서 예상과 다른 부분이 하나 있다

정확도는 문제없다.

cold/warm 세 쌍 모두 정답이다. 

그런데 `inference_wall_seconds`를 직접 집계해 보면:

| case              |    cold |     warm | warm/cold |
| ----------------- | ------: | -------: | --------: |
| same_structure    | 3.36 ms | 10.39 ms | **3.10×** |
| counterfactual    | 3.24 ms | 13.54 ms | **4.17×** |
| renamed_reordered | 3.25 ms | 10.27 ms | **3.16×** |

즉 **warm이 오히려 전부 느리다.**

평균으로 보면:

```text
cold ≈ 3.28 ms
warm ≈ 11.40 ms
```

이다.

이건 꽤 중요한 결과다.

현재 R0.2에서:

> `circuit reuse = 계산 효율 증가`

라고 wall-clock 관점에서 말할 수 없다.

오히려 현재 Python reference engine에서는:

```text
circuit recall
+ binding scan
+ activation pool
+ candidate competition
```

등의 오버헤드가 graph-only 비용보다 더 큰 가능성이 있다.

다만 이것도 **현재 wall time만 보고 원인을 확정한 건 아니다.**

로드맵에서 처음부터 분리하기로 했던:

```text
dependency operations
binding operations
candidate circuits
signal events
kernel ticks
proof reconstruction
```

을 봐야 한다.

즉 이 결과는 가설을 반박했다기보다는:

> **구조적 압축과 실제 실행시간 단축은 동일한 것이 아니다.**

라는 걸 보여준다.

이 차이는 앞으로 굉장히 중요하다.

# 5. Novelty에서도 같은 현상이 있다

`longer_composition`:

```text
graph_only ≈ 4.02 ms
full       ≈ 14.86 ms
```

`branched_composition`:

```text
graph_only ≈ 2.97 ms
full       ≈ 9.47 ms
```

둘 다 정확도와 proof D는 동일하다. 

따라서 현재 구현에서는:

```text
circuit 기능을 켠 full
```

이 graph-only보다 wall-clock 성능 이점은 없다.

이건 나쁜 결과라기보다는 **reference engine에서 알고리즘 의미를 먼저 검증한다는 현재 목적에 부합한다.**

하드웨어 효율성이나 sparse/event-driven 이득을 이 결과에 바로 연결하면 안 된다.

# 6. training 3 vs training 9에서는 예상했던 trade-off가 아직 안 보인다

둘 다 `matched_weak_conflict`에서 동일한 형태다.

### training 3

```text
attempt 1: false, D=3
attempt 2: true,  D=2
```

### training 9

```text
attempt 1: false, D=3
attempt 2: true,  D=2
```

 

시간도 거의 같다.

내 집계:

```text
training 3
wrong: 10.61 ms
fix:    2.92 ms

training 9
wrong:  9.49 ms
fix:    3.02 ms
```

즉 현 단계에서는:

> 학습을 더 많이 하면 attractor가 더 강해져 수정 비용이 커진다.

라는 **Compression ↔ Flexibility trade-off는 관찰되지 않았다.**

그렇다고 없다고 결론 내릴 단계도 아니다.

현재 training count 3/9가 실제 `attractor strength`를 충분히 다르게 만들었는지부터 확인해야 한다.

# 7. Binding/Proof 쪽에서는 이상 징후가 없다

36개 전부에서 내가 확인한 결과:

```text
assumption_ids_outside_public_observation = 0
assumption_ids_outside_last_program_paths = 0
proof_paths_outside_last_program = 0
```

였다.

즉 최소한 기록된 관계 기준에서는:

* 입력에 없던 edge를 proof에 몰래 끼워 넣은 흔적 없음
* 마지막 program 밖의 assumption 없음
* program에 없는 proof path 없음

이다.

보고서도 이 공집합은 **포함관계상 이상 없음**을 의미한다고 명시한다. 

이 부분은 꽤 좋다.

즉 현재 오답은:

> proof가 망가져서 나온 오답

으로 보이지 않는다.

오히려:

> **잘못된 assumption 아래에서는 논리적으로 유효한 proof를 만들고 안정적으로 틀림**

이라는 기존 R0.1/R0.2 설계 의도가 그대로 나타난다.

# 8. 하지만 Decision ≠ Explanation 가설은 아직 검증 못 했다

모든 record가:

```text
actual_causal_path_reconstructed = false

separate_explanation_event_recorded = false
separate_readout_event_recorded = false
```

다.

```text
causal_explanation_verified = false
```

라고 명확히 남아 있다. 

그래서 현재 말할 수 있는 것은:

```text
결정에 붙은 proof가
당시 public observation/program 범위 안에 있었다
```

아직:

```text
실제 판단을 만든 계산 경로
```

를 비교한 게 아니다.

따라서 `Decision Generation ≠ Explanation Reconstruction`은 여전히 후속 실험 대상이다.

# 10. 지금 R0.2에서 가장 강하게 말할 수 있는 것

현재까지의 결과를 합치면:

> **R0.2는 반복 성공 구조를 회로로 저장·재사용하고, 여러 회로 후보를 활성화하며, 잘못된 안정 상태를 실제로 만들 수 있고, 오류 뒤 추가 관측·재확장을 허용하면 동일 episode에서 다른 계산 구조를 사용해 결론을 수정할 수 있다.**

여기까지는 꽤 강하다.

반면 아직 말하면 안 되는 것은:

> 회로 압축이 실행시간을 줄였다.

현재 결과는 오히려 wall-clock에서는 반대다.

또:

> 한번 수정한 회로가 이후 비슷한 새 episode에서도 자동으로 수정된 판단을 유지한다.

이것도 현재 `retention/reload` 때문에 성립하지 않는다.

그리고:

> training을 많이 할수록 강한 attractor가 생겨 수정하기 어려워진다.

이 역시 현재 3/9 비교에서는 확인되지 않았다.

# 11. 그래서 다음 작업 우선순위가 더 명확해졌다

지금 바로 R0.2.1로 넘어갈 수도 있지만, 나는 **기준선에서 한 가지를 더 끝내고 가는 게 좋다.**

우선순위는:

```text
1. retention/reload 재오답 원인 분리
2. cold/warm의 상세 operation cost 비교
3. 그 결과를 R0.2 기준선 문서에 고정
4. R0.2.1 snapshot / restore / resume
```

이다.

특히 1번이 중요하다.

현재 가장 큰 미해결 질문은:

> **왜 feedback으로 수정된 시스템이 새 episode에서는 다시 이전 assumption 기반 attractor로 들어갔는가?**

다.

이걸 밝혀야 이후 R0.4의 circuit plasticity나 R0.5의 persistent dynamics를 설계할 때:

```text
episodic correction
vs
long-term circuit learning
```

을 제대로 분리할 수 있다.

그리고 2번에서는 wall time 말고 실제로:

```text
graph expansions
binding operations
candidate circuit scans
kernel ticks
signal events
```

를 비교해야 한다.

**현재 review 결과는 기대했던 가설에 맞춰 예쁘게 나온 게 아니라, 오히려 “회로 재사용은 되지만 현재 구현에서는 더 비싸고, 수정은 가능하지만 아직 일반화되지는 않는다”라는 중요한 경계선을 보여준다.** 이게 지금 R0.2 기준선에서 가장 가치 있는 결과라고 본다.
