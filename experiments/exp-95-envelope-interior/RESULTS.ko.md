# R49 / EXP-95 결과: R48 전이 프로브의 모서리는 최악 경계가 아니었고 실제 파이프라인 입력도 구간을 벗어났지만, 벗어난 크기는 판정 여유의 백만 분의 일 수준이며 판정은 전부 유지됐다

[설계](DESIGN.ko.md)(SHA-256 `bdc5c8fd…88d58`)와 [동결 spec](frozen_spec.json)(`bc05228b…3f48b`), [입력 핀](input_manifest.json)(`da1c7ace…6589`)은 실행 전에 고정했고 실행 뒤 바꾸지 않았다. 본 실행 1회, 같은 명령의 결정성 재실행 1회. 번호 R49 / EXP-95는 잠정이다.

## 1. 판정 (설계 5절 규칙 그대로)

| 항목 | 판정 | 핵심 수치 |
|---|---|---|
| C0 통제: 로컬 809-settle 재계산 | `EXACT` | `transfer.json` 10개 구획과 `roles.json`이 `network_id`를 빼고 값 전체 일치 |
| A 포함: 실제 R48 파이프라인의 단계 입력·출력 | **`NOT_COVERED`** | `query` 입력 2,106개 중 318개(고유 trace 77/234, 참조 200/512)가 프로브 구간 밖, 최대 2.69e-6 |
| B1 의미 보존: 7개 단계·arm | `PRESERVED` 7/7 | 101,841 내부점 settle에서 불일치 0, 전부 `stable_decision` |
| B2 극값성: `or0..4` (전수 69,905) | `NOT_REFUTED_IN_SAMPLE` | 관측 출력 범위가 R48 구간과 끝값까지 동일 |
| B2 극값성: `projection0/1` | **`REFUTED`** | 출력 10,368개 중 2,368개(행 1,104/2,592)가 구간 밖, 최대 1.76e-7 |
| B2 극값성: `feasible4` | **`REFUTED`** | 출력 25,920개 중 2,306개(행 881/5,184)가 구간 밖, 최대 2.69e-6 |

한 문장으로: **R48이 "최악 내부 마진 모서리"라 부른 점들은 표본 안에서 이미 최악이 아니었고, R48 자신의 768 평가 중 native 512건의 39%(200건)는 `query4` 입력이 프로브가 가정한 구간 밖에 있었다. 그러나 모든 초과는 3e-6 미만이고, 판정 임계(0.35/0.65)까지의 최소 여유 0.328과 비교하면 여섯 자릿수 작으며, 구간을 1e-3 넓힌 arm을 포함해 판정이 바뀐 사례는 0건이다.**

R48의 768 평가 결과와 448짝 의미 불변 판정은 이 결과로 바뀌지 않는다. 바뀌는 것은 809-settle 프로브의 지위다. 그것은 "구간 전체에 대한 충분조건"이 아니라 "모서리 점들에서의 관측"이며, 충분조건으로 쓰려면 구간에 여유(slack)를 명시해야 한다.

## 2. A: 실제 파이프라인은 프로브 구간 안에 있었는가 (저장 자료, 새 settle 0)

R48 서버 raw의 `batch00..11`이 참조하는 고유 trace 711개(참조 32,832회)를 단계별로 검사했다.

| 단계 | 고유 trace / 참조 | 입력 구간 밖 | 출력 구간 밖 | 최대 초과 |
|---|---:|---:|---:|---:|
| `role` | 64 / 18,304 | (검사 대상 아님) | (검사 대상 아님) | — |
| `pair` | 16 / 9,152 | 0 / 48 | 0 / 16 | 0 |
| `or0..4` | 180 / 4,096 | 0 / 504 | 0 / 180 | 0 |
| `projection0/1` | 102 / 256 | 0 / 408 | 35 / 408 (trace 23, 참조 48) | 1.54e-9 |
| `feasible` | 115 / 512 | 4 / 575 (trace 1, 참조 8) | 86 / 575 (trace 21, 참조 200) | 입력 8.4e-14, 출력 2.69e-6 |
| `query` | 234 / 512 | 318 / 2,106 (trace 77, 참조 200) | (다음 단계 없음) | 2.69e-6 |

- `pair`의 실제 입력은 4개 role 대표값의 drive와 **정확히** 같았고, `pair`·`or` 단계는 입력·출력 모두 구간 안이었다. 설계 때 예상한 "role 동치류 내부 1e-17 편차의 전파로 인한 이탈"은 이 두 단계에서 나타나지 않았다(예측 틀림).
- 이탈은 `projection` 출력부터 시작해 `feasible` 출력, `query` 입력으로 이어진다. `query`의 `e` 입력은 `feasible`의 eligibility 출력 그대로이므로 두 단계의 참조 200건·최대 2.69e-6이 일치한다.
- 독립 경로 재계산: trace의 `final_vector`가 아니라 batch 기록의 값 필드(`messages`, `applied`, `binding.eligibility`, `binding.coverage_activation`)로 다시 세어도 projection 48/256, feasible 200/512, membership 0으로 같았다([verification.json](../../evidence/envelope-interior-20261120-r49/verification.json)).

## 3. B: 구간 내부점 (새 로컬 settle 101,841 + 통제 809 = 102,650)

| 단계 / arm | settle | 판정 불일치 | 구간 밖 출력 | 최대 초과 | 최소 판정 여유 | tick 범위 |
|---|---:|---:|---:|---:|---:|---|
| `or` / envelope (전수) | 69,905 | 0 | 0 / 69,905 | 0 | 0.3383 | 25–30 |
| `projection` / envelope | 2,592 | 0 | 2,368 / 10,368 | 1.76e-7 | 0.3281 | 29–32 |
| `projection` / inflated(δ=1e-3) | 2,592 | 0 | (검사 안 함) | — | 0.3281 | 29–32 |
| `feasible` / envelope | 5,184 | 0 | 2,306 / 25,920 | 2.69e-6 | 0.3490 | 28–38 |
| `feasible` / inflated | 5,184 | 0 | (검사 안 함) | — | 0.3490 | 28–38 |
| `query` / envelope | 8,192 | 0 | (하류 구간 없음) | — | 0.3374 | 28–34 |
| `query` / inflated | 8,192 | 0 | (하류 구간 없음) | — | 0.3374 | 28–34 |

반례의 예([analysis.json](../../evidence/envelope-interior-20261120-r49/analysis.json)의 `witnesses`, 단계별 상위 40개 보존):

- `projection0`, 패턴 `[F,F,T,T]`, 네 입력 모두 구간 **상한**: 거짓 출력 `e0 = 0.021949858876…`으로 R48 `false_max = 0.021949682427…`보다 1.76e-7 크다. R48 모서리는 참 입력을 **하한**(`true_min`)에 두었는데, 거짓 출력이 가장 커지는 것은 참 입력이 상한일 때였다. 즉 "참 입력은 낮을수록, 거짓 입력은 높을수록 나쁘다"는 좌표별 단조 가정이 이 프로그램에서 성립하지 않는다.
- `feasible`, `via_projection`, 패턴 none, 네 입력 모두 구간 하한: eligibility `1.3062e-5`로 R48 `false_min = 1.5754e-5`보다 2.69e-6 작다(임계에서 멀어지는 방향).

저장한 반례 80개는 R33 `kernel` 래퍼를 거치지 않고 `hcr.dynamics.settle`을 직접 호출해 다시 계산했고, 출력·tick·초과량이 80/80 비트 단위로 같았다.

## 4. 사후 탐색 분석: 초과의 방향 (사전 등록하지 않음)

설계에는 없던 분해다. 초과를 "임계 쪽(해로운 방향)"과 "임계 반대쪽(무해한 방향)"으로 나눴다. 같은 실행 자료의 재분석이며 새 settle은 없다.

| 위치 | 해로운 방향 최대 | 무해한 방향 최대 |
|---|---:|---:|
| A 실제 파이프라인: projection 출력 | 1.54e-9 (32개 값) | 2.0e-13 |
| A 실제 파이프라인: feasible eligibility | 0 | 2.69e-6 (800개 값) |
| A 실제 파이프라인: feasible coverage | 0 | 7.1e-12 |
| B projection 거짓 / 참 출력 | 1.76e-7 / 2.05e-9 | 8.4e-14 / 1.6e-11 |
| B feasible 거짓 / 참 eligibility | 7.5e-11 / 1.5e-11 | 2.69e-6 / 1.59e-6 |
| B feasible coverage 참 | 3.4e-11 | 7.1e-12 |

- 실제 파이프라인에서 관측된 가장 큰 이탈(2.69e-6)은 전부 무해한 방향이다. 해로운 방향 이탈은 projection 출력의 1.54e-9가 최대다.
- 내부점 표본 전체에서 해로운 방향 최대는 1.76e-7, 모든 단계·arm의 최소 판정 여유는 0.328이므로 비율은 약 1.9e6이다. 이 비율은 표본에서의 관측이며 구간 전체의 상계가 아니다.

## 5. 왜 이 질문이 프로젝트 가설과 닿는가

이 실험은 `A_n`의 수렴 결과가 `A_(n+1)`의 입력 노드가 된다는 H02의 계산적 전제 한 가지를 수치로 본 것이다. R48 파이프라인의 각 단계는 앞 단계 수렴 상태의 연속값을 그대로 drive로 받는다. 수렴 상태는 "참/거짓"이라는 기호가 아니라 주변 입력 조합에 따라 달라지는 실수이므로(이번 관측에서는 구간 끝값 대비 최대 3e-6 미만), 승격이 의미를 보존하려면 다음 단계의 판정 여유가 그 흔들림보다 커야 한다. 이번 범위에서는 여유가 약 여섯 자릿수 컸다. 이것은 수작업 Program과 authored codebook에서의 관측이고, 학습으로 형성된 회로·자율 승격·더 깊은 계층·다른 Config에서 같은 여유가 유지되는지는 보지 않았다. H02의 상태를 바꾸는 증거로 올리지 않는다.

## 6. 실행·검산·비용

- 호스트: Linux x86_64, glibc 2.39, Python 3.12.3. worker 1, retry 0, 학습 0, `World.measure` 0(호출 시 예외로 차단). 엔진(`src/hcr`)과 R19~R48 도구는 수정하지 않았다.
- 본 실행: wall 114.3초, CPU 113.2초. 행 스트림 SHA-256 `ee4d5ab0…360b1`(101,841행).
- 결정성 재실행 1회: 시간 필드를 뺀 모든 필드와 행 스트림 digest 동일([determinism.json](../../evidence/envelope-interior-20261120-r49/determinism.json)).
- 2차 경로 검산 [verification.json](../../evidence/envelope-interior-20261120-r49/verification.json): 기준 구간을 `*_bounds`가 아닌 개별 행에서 다시 만들어 일치 확인, 반례 80/80 직접 재settle 일치, 포함 검사 재계수 일치, `status = PASS`. 같은 작성자의 검산이며 독립 감사가 아니다(`independent_auditor = false`).
- core 회귀시험(`scripts/selftest.py`)은 변경 뒤 다시 실행해 결과를 커밋 요약에 적었다. 이번 변경은 새 파일 추가뿐이고 기존 파일은 건드리지 않았다.
- 내부점 101,841행 자체는 저장하지 않았다(행 digest, 단계별 집계·관측 범위, 반례 상위 40개씩만 저장). 같은 명령으로 재생성해 digest를 대조할 수 있다: `python3.12 -B tools/r49_envelope_interior/probe.py --out <새 폴더>`.

## 7. 공개해야 할 절차상 사실

1. 설계·spec 작성 → 도구 작성 → `--smoke` 구조 점검(405행) → 본 실행 순서였다. smoke 출력에 판정 요약이 포함되어 있어 **본 실행 전에** A의 `NOT_COVERED`와 projection 첫 패턴의 `REFUTED`를 이미 보았다. 그 뒤 설계·spec·도구의 판정 논리는 바꾸지 않았다(해시 동일). smoke는 증거로 세지 않는다.
2. 설계의 사전 예측 중 "B1 전부 보존"은 맞았고, "B2에서 1e-6 근방 초과 가능"은 방향은 맞았으나 원인 설명(종료 tick 불연속)은 검증하지 않았다. projection 반례는 종료 tick이 아니라 입력 조합의 비단조성으로 보이지만 이것도 확인하지 않은 해석이다. "A는 role 편차 전파로 깨질 수 있다"는 예측은 틀렸다(이탈은 projection 이후에서만 발생).
3. 4절의 방향 분해는 결과를 본 뒤 추가한 탐색 분석이다.
4. 설계·구현·실행·검산을 한 작성자(AI 연구 보조)가 한 세션에서 수행했다. R48 등에서 쓰인 blind 방향 토론·교차검토·별도 Judge는 거치지 않았다.

## 8. 한계

- B2~B4는 격자와 고정 무작위 표본이다. `PRESERVED`는 구간 전체의 의미 보존 증명이 아니고, 관측된 최대 초과는 진짜 최대의 하계일 뿐이다. `query`는 패턴당 16개 배정만 보았다(9차원 격자 3^9의 0.08%).
- B1의 전수는 서버 표의 16개 pair 출력값에 대한 것이다. A가 실제 `or` 입력이 pair 구간 안임을 확인했지만 "16개 값 중 하나"임을 직접 확인하지는 않았다.
- 기준 구간 자체가 R48 모서리 관측에서 온 것이므로, 이번에 넓어진 구간을 다시 하류에 주입하는 반복(고정점까지의 구간 폐포)은 하지 않았다.
- C0는 같은 코드의 다른 호스트 재실행이다. 서버 libc 버전은 원 기록에 없어 UNKNOWN이고, 값이 정확히 같았다는 사실을 서로 다른 libm 사이의 재현성으로 확대하지 않는다. R48 전체 파이프라인(33,753 settle)의 로컬 재실행은 하지 않았다.
- 학습된 표현, H03 구조 재사용, 원계산 대체, 속도·효율에 관한 증거가 아니다. 새 독립 표본 0.

## 9. 다음 후보 (이번 사이클에서 시작하지 않음)

1. **구간 폐포의 인증**: 표본이 아니라 구간 산술로 "입력이 구간 ⊕ slack 안이면 출력 분류가 유지되고 출력이 다음 구간 ⊕ slack 안"을 단계별로 증명. 종료 tick이 입력에 따라 달라지는 것이 난점이라 10/12~10/15의 단일 궤도 인증보다 어렵다. 먼저 `or`·`projection`처럼 얕은 프로그램에서 가능한지 본다.
2. **R48 전체의 다른 호스트 재실행**: 보존된 source 163개(현재 checkout과 해시 일치 확인함)로 `probe.py --phase run`을 그대로 돌려 서버 manifest와 바이트 대조. 원 기록의 `local_native_calls_added = 0`, host attestation 부재를 직접 메운다.
3. **Attractor Width의 측정**(동기 문서의 고정관념 가설): 이번의 "여유 대 흔들림"을 뒤집어, 입력을 구간 밖으로 단계적으로 밀었을 때 판정이 처음 바뀌는 거리와 그때의 실패 형태(오확정인지 기권인지)를 단계별로 잰다. R48의 `native_marginal`이 상관 소실에서 오확정 0·기권 128이었던 것과 같은 "안전한 실패"가 수치 섭동에서도 유지되는지가 질문이다.
