# R52 / EXP-98 결과: 경로가 둘이어도 수렴 지연은 "쓴 경로의 증거를 보는" 입력 규칙을 넘지 못했다. 대신 회로가 증거가 더 약한 경로를 골라 쓴다는 것이 드러났다

[설계](DESIGN.ko.md)(SHA-256 `00ac4b7e…f262`), [동결 spec](frozen_spec.json)(`85ecc367…8eaf`), [입력 핀](input_manifest.json)(`4d6db79f…e2df`)은 본 실행 전에 고정했고 실행 뒤 바꾸지 않았다. 본 실행 1회, 결정성 재실행 1회. 번호 R52 / EXP-98은 잠정이다.

## 1. 판정 (설계 8·9절 규칙 그대로)

**해석: `SLOWDOWN_REDUNDANT_AGAIN`.** 주 신호 `ticks_total`은 "어느 edge든 증거 ≤ 0" 규칙은 이겼지만(AUC +0.083), "쓴 경로에 증거 ≤ 0인 edge가 있는가" 규칙에는 0.043 뒤졌다. 설계의 기준(두 단순 규칙 모두를 0.05 이상 앞설 것)을 채우지 못했다.

| 예측 | 판정 | 내용 |
|---|---|---|
| P1 `simple_any`는 재현율 1.0, 보존율 < 0.7 | supported | 재현율 1.0, 재사용 보존율 0.465 |
| P2 `ticks_total` AUC ≥ 0.80 | supported | 0.881 |
| P3 `ticks_total` − `simple_any` ≥ 0.05 | supported | +0.083 |
| P4 `structure_aware` ≥ `ticks_total` | supported | 1.000 대 0.881 |
| P5 이월 문턱 70이 무너진다 | **falsified** | 재현율 1.0, 보존율 0.526(기준 0.5 이상). 간신히 버텼다 |
| P6 `selected_route`가 둘 사이 | supported | 0.798 < 0.924 ≤ 1.000 |

## 2. 신호별 결과 (시험 memory 4개, 적용 대상 974셀, 표적 114 = 포획형 107 + 미결정형 7)

회로 OFF의 판단은 256개 입력 전부에서 "두 경로 중 하나라도 둘째 edge 증거가 양수이면 True"였다.

| 신호 | 필요한 것 | AUC | 재현율 | 재사용 보존율 | 보류한 셀 |
|---|---|---:|---:|---:|---:|
| `structure_aware` (모든 경로에 증거 ≤ 0) | 입력 + 전체 경로 구조 | 1.000 | 1.000 | 1.000 | 114 |
| `ticks_decision` (≥ 35) | ON 실행 | 0.925 | 1.000 | 0.805 | 282 |
| `selected_route` (쓴 경로에 증거 ≤ 0) | 입력 + 어느 회로를 썼는지 | 0.924 | 1.000 | 0.805 | 282 |
| `ticks_total` (≥ 70, 주 신호) | ON 실행 | 0.881 | 1.000 | 0.526 | 522 |
| `ticks_pool` (≥ 35) | 회로 적용 전 | 0.831 | 1.000 | 0.474 | 566 |
| `simple_any` (어느 edge든 증거 ≤ 0) | 입력만 | 0.798 | 1.000 | 0.465 | 574 |
| `goal_margin` | ON 실행 | 0.420 | 0.728 | 0.135 | 827 |

- **문턱은 chain에서 그대로 넘어왔다.** diamond 보정 memory에서 다시 계산한 문턱이 R51의 값과 같았다(`ticks_total` 70, `ticks_pool` 35, `ticks_decision` 35, 입력 규칙 0). 그래서 이월·재보정 두 평가의 수치가 같다.
- **구조를 아는 규칙은 완벽하다.** 모든 경로를 훑어야 계산할 수 있는 규칙이고, 사실상 회로 없이 그래프를 푸는 것과 같다.
- **`ticks_decision`과 `selected_route`는 같은 282셀을 골랐다**(사후 확인). decision network의 tick이 35 이상이라는 것과 "회로가 적용된 경로에 증거가 0 이하인 edge가 있다"는 것이 이 격자에서 정확히 같은 조건이다.
- **pool tick은 판단 뒤 tick보다 못하다.** pool은 쓰지 않을 경로가 흐릿해도 느려진다.
- `goal_margin`은 이번에도 쓸모없다(R51과 같음).

비용(시험 memory의 1,024셀, 재보정 문턱):

| 정책 | kernel tick 합 | expansion 합 |
|---|---:|---:|
| always-OFF | 48,748 | 2,432 |
| always-ON | 88,557 | 1,121 |
| `ticks_decision` 또는 `selected_route` gate | 106,545 | 1,883 |
| `ticks_total` gate | 118,285 | 2,483 |
| `structure_aware` gate (ON 실행 뒤 판정한 경우) | 95,979 | 1,463 |

always-OFF가 tick으로는 가장 싸다는 점, 회로의 이득이 expansion뿐이라는 점은 R51과 같다.

## 3. 사후에 드러난 것: 회로는 증거가 더 약한 경로에 붙는다 (사전 예측 아님)

`ticks_decision`과 `selected_route`가 "틀리게" 보류한 168셀을 들여다보니 한 가지 양상이었다. 아래는 모두 결과를 본 뒤의 탐색 분석이며 [verification.json](../../evidence/slowdown-diamond-20261120-r52/verification.json)의 `exploratory`에 별도 코드로 다시 계산해 두었다.

- **두 경로 증거가 모두 양수이고 크기가 다른 360셀 전부에서, 회로는 증거가 더 약한 경로에 적용됐다**(360/360).
- **한 경로만 깨끗한(증거 양수) 460셀 중 168셀에서, 회로는 깨끗한 경로가 아니라 증거가 0 이하인 경로에 적용됐고 그대로 True가 채택됐다.** 예: n=20, 경로 A의 둘째 edge −0.2, 경로 B의 둘째 edge +0.8. ON은 경로 A만 전개해 goal 0.998로 True. OFF는 A를 전개했다가 B까지 가서 True.
- 이 168셀은 회로를 꺼도 True라서(다른 경로가 받쳐 주므로) 설계의 표적 정의로는 "판단이 안 바뀐 셀"이다. 그러나 ON이 True에 도달한 **경로**는 증거가 반대인 경로다. R50·R51의 포획과 같은 과정이 일어났고, 결과만 우연히 맞았다.
- 회로가 적용된 경로의 증거가 0 이하인 셀은 282개이고, 그중 114개가 표적(판단이 바뀜), 168개가 위와 같이 다른 경로에 가려진 경우다. `ticks_decision ≥ 35`는 이 282셀을 정확히 골랐다(이 기준으로 본 AUC 1.000). 다만 `selected_route` 규칙도 정의상 같은 282셀을 고르므로 tick의 고유 정보는 아니다.

코드에서 읽히는 유력한 이유: prior drive가 `max(1 − |score|)`에 비례하므로 증거가 흐릿한 경로일수록 회로 후보가 더 큰 prior를 받고, pool 경쟁에서 그 후보가 이긴다. 이 설명은 prior 항을 떼어 내는 대조로 확인하지 않았다.

이 관찰이 맞다면 두 가지를 뜻한다.

1. **표적을 "판단이 바뀌었는가"로 잡으면 과정상의 포획을 놓친다.** tick과 `selected_route`가 재사용 보존율에서 손해 본 것(0.805)은 이 가려진 포획을 보류했기 때문이다. "틀린 보류"가 아니라 "답은 맞지만 근거 경로가 반대 증거인 판단"을 잡은 것이다.
2. **수렴 지연은 결과가 아니라 과정을 잰다.** R51의 "가장 느린 셀은 판단이 바뀐 셀이 아니었다"와 같은 방향이다. 판단 뒤 tick은 "방금 쓴 경로에서 prior가 증거를 눌렀는가"를 정확히 따라간다.

판단과 근거 경로가 어긋나는 이 양상은 H08(판단 생성과 설명 복원의 분리)과 닿아 있지만, 이번 실험은 proof 내용을 검사하지 않았으므로 H08의 근거로 올리지 않는다.

## 4. 이 결과가 뜻하는 것과 뜻하지 않는 것

- 사전에 정한 질문("경로가 둘이면 tick이 입력 규칙을 이기는가")의 답은 **아니오**다. "어느 edge든"이라는 가장 거친 규칙은 이겼지만, 엔진이 이미 알고 있는 "어느 회로를 썼는가"만 더하면 입력 규칙이 판단 뒤 tick과 같아진다.
- tick 신호의 고유 가치는 두 사이클 연속으로 확인되지 않았다. 이 엔진에서 tick이 알려 주는 것은 입력과 "어느 회로를 썼는지"에서 계산되는 것과 같다. 엔진 내부에서 그 계산이 공짜로 따라온다는 뜻이기도 하지만, 그것을 "입력 규칙이 못 잡는 것을 잡는다"고 말할 수는 없다.
- 판단이 **실제로 바뀌는** 입력만 고르려면 모든 경로의 증거를 봐야 한다. 그것은 회로를 쓰는 이득(expansion 절감)과 맞바꾸는 일이다.
- 3절의 "약한 경로 선호"는 사후 관찰이다. 다른 topology·다른 첫 edge 증거·prior 정책에서도 성립하는지, 원인이 prior의 불확실성 항인지는 시험하지 않았다.

## 5. 실행·검산

- 기록 호스트: Linux x86_64, glibc 2.39, Python 3.12.3. `src/hcr` 수정 0, `World.measure` 0, revision 요청 0, feedback 소비 20(학습). ON 평가 1,536, OFF 평가 256.
- memory 6개(n = 3, 6, 8, 9, 15, 20)의 문서 해시가 R51 기록과 같음을 실행 중 확인했다.
- 본 실행 wall 28.7초. 결정성 재실행에서 시간 필드를 뺀 전 필드 동일([determinism.json](../../evidence/slowdown-diamond-20261120-r52/determinism.json)).
- 2차 경로 검산 [verification.json](../../evidence/slowdown-diamond-20261120-r52/verification.json), 기록 호스트에서 `status = PASS`.
  - `AdaptiveSession`으로 다시 학습해 memory 6개를 비트 단위로 재구성.
  - 1,792 평가 전부를 `AdaptiveSession`으로 다시 실행. 채택값·status·적용된 회로 구간·전개 경로·expansion·network별 tick이 1,792/1,792 일치(필수).
  - 표적, 문턱, AUC, 재현율, 보존율, 판정, 해석을 probe와 별도 코드로 재계산해 일치(필수).
  - goal 상태의 부동소수 값과 `goal_margin`은 진단으로만 보고(기록 호스트에서 차이 0).
  - AUC·표적 분류의 순수 함수는 R51의 `core.py`를 probe와 검산이 함께 쓴다. 같은 작성자의 검산이며 독립 감사가 아니다.
- core 회귀시험(`scripts/selftest.py`)은 변경 뒤 다시 실행했다. 이번 변경은 새 파일 추가뿐이다.

## 6. 공개해야 할 절차상 사실

1. 순서: 엔진 동작 확인 1회(n=3 memory, 네 edge 모두 1.0인 diamond, ON·OFF. 설계 2절에 기록) → 설계·spec 동결 → 도구 작성 → `--smoke`(학습 3 episode) → 본 실행. 본 실행 전에 격자 평가 결과는 보지 않았다.
2. 2절의 "같은 282셀"과 3절 전체는 결과를 본 뒤 추가한 탐색 분석이다. 3절이 이 문서에서 가장 흥미로운 부분이지만 사전 등록된 발견이 아니다.
3. 해석 `SLOWDOWN_REDUNDANT_AGAIN`은 주 신호를 `ticks_total`로 고정한 규칙에 따른 것이다. `ticks_decision`을 주 신호로 삼았어도 `selected_route`와 차이가 0.001 미만이라 결론은 같다.
4. P5("이월 문턱이 무너진다")는 R51의 P3에 이어 두 번째로 틀렸다. 다만 보존율 0.526은 기준 0.5를 간신히 넘은 값이고, 절반 가까운 정상 재사용을 잃는 문턱을 "유지됐다"고 부르기는 어렵다.
5. 설계·구현·실행·검산을 한 작성자(AI 연구 보조)가 한 세션에서 수행했다. blind 토론·교차검토·별도 Judge는 없었다.

## 7. 한계

- diamond 하나, 첫 edge 둘은 1.0 고정, 길이 2 회로 하나, 기본 Config의 결정적 격자 비교다. 독립 표본이 아니고 AUC는 이 격자의 순위 통계다. 격자 간격 0.1.
- 두 경로가 같은 pattern을 쓰는 대칭 구조다. 경로 길이가 다르거나 회로가 여럿인 경우, 경로가 셋 이상인 경우는 보지 않았다.
- 보류는 새 정보 없이 OFF를 채택하는 것이라 R51의 영합은 그대로다. 표적 114셀의 포획형 107건은 닫힌 세계에서 오답이고 열린 세계에서는 올바른 보완이다.
- tick 수가 다른 호스트에서도 같은지는 그쪽에서 검산을 돌려야 확인된다(R50·R51에서는 같았다).
- 인간의 직관, LLM 내부, 생물학에 대한 주장이 아니다.

## 8. 다음 후보 (이번 사이클에서 시작하지 않음)

1. **약한 경로 선호의 원인 대조**: 3절의 관찰을 사전 등록해 다시 시험한다. 강도가 거의 0인 합성 memory(R50의 `b3@0.022`)에서는 선호가 사라지는지, `route_only`에서도 같은지, 첫 edge 증거를 바꾸면 어떻게 되는지 본다. 엔진 변경 없이 가능하고, "습관은 증거가 가장 흐릿한 곳에 붙는다"가 이 엔진의 일반 성질인지 가린다.
2. **가려진 포획과 proof**: 168셀에서 ON이 내놓는 proof가 실제로 반대 증거 edge를 "열림"으로 가정하는지 검사한다. 답은 맞고 근거는 틀린 판단을 엔진의 기존 진단(R0.3.2 grounding)이 잡는지 본다. H08에 대한 첫 직접 자료가 될 수 있다.
3. **보류 뒤 측정 요청**(R51에서 이월): 이제 무엇을 측정할지가 분명하다. 회로가 적용된 경로에서 증거가 0 이하인 edge다.
4. **고착 규칙 계약 심사**(R50에서 이월).
